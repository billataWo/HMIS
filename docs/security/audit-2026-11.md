# Security audit and remediation, November 2026

For the HMIS team. A full pass over the web app (`apps/web`), the API (`apps/api`) and the database
(`packages/db`), against the hardening checklist in six parts: authentication, authorization and
clinic isolation, input and web protections, secrets and git history, configuration and
dependencies, and verification. Audited 2026-11-11 on `main` at `cd80832` plus the working tree.

**Summary.** No critical issue was found: clinic isolation (row-level security), parameterized
queries, server-side prices, secure session cookies and the security headers were already in place.
Nine weaknesses were fixed; five items are recorded as not applicable or accepted, with reasons.
No secret was ever committed to git, so nothing needs rotating because of the repository.

## 2. Controls checked and already in place

| Control | Evidence |
|---|---|
| Clinic isolation in the database | Row-level security on every clinic table (`packages/db/prisma/migrations/20261106000000_row_level_security`); the API's everyday role `hmis_app` is not the owner, so policies apply; the tenant is set per transaction (`packages/db/src/index.ts`). Exports, deletion and sync refuse to run if any clinic table lacks it (`sync/engine.ts`, `exports/clinic-data.ts`). |
| Isolation in the API | Every query also filters by the signed-in clinic. Tested: another clinic's patient, visit and export answer 404, and the database role sees 0 rows of another clinic in all 32 clinic tables. |
| Console (HMIS staff) | Separate sign-in and signing key, two-step sign-in required, roles Owner / Billing / Support on every action, every action in History. |
| Sessions | 12-hour token in an httpOnly, SameSite=Lax, Secure (production) cookie (`apps/web/src/app/actions.ts:48`, `two-step-actions.ts:13`); console cookie SameSite=Strict, path `/platform` (`apps/web/src/app/platform/actions.ts:11`). The account, role and clinic are re-read on every request; a password change or reset ends every other session. |
| Sign-in guessing | Limits per account, per address and per pair, with audit entries; unknown accounts take as long as known ones. Two-step codes work once and lock after 5 wrong. |
| Server-side money | Charges take their price from the price list (`visits/visits.controller.ts:208`, `pharmacy/pharmacy.controller.ts:163`, `lab/lab.controller.ts:147`); invoices are totalled on the server; discounts are admin-only, at most the bill, with a reason and an audit entry (`billing/billing.controller.ts:144,183`); payments are capped at the balance. HMIS's own invoices and online payments count only what the provider confirms. Tested: a price sent by the client is ignored. |
| SQL injection | Prisma's parameterized queries everywhere. The few raw statements take identifiers from the database catalogue only, quoted, with values as parameters (`sync/engine.ts`, `exports/clinic-data.ts`). |
| Request validation | Zod schemas on every request body (`common/zod.pipe.ts`), plus F5 and F6. Bodies are limited to 2 MB (`configure.ts`). |
| XSS | React escapes all output; no `dangerouslySetInnerHTML` anywhere. Content Security Policy: scripts, connections and frames only from the site itself (`apps/web/next.config.ts:45`). |
| Other headers | `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: same-origin`, `Permissions-Policy`, HSTS one year in production (`next.config.ts:51`); no `X-Powered-By`, no server banner. Verified on a production build. |
| CSRF | The API takes bearer tokens only (no cookies), so browsers cannot forge its requests; server actions are checked by Next.js against the site's origin; route handlers per F8. |
| HTTPS | Own servers: Caddy serves HTTPS only and redirects HTTP (`deploy/caddy/Caddyfile`). AletCloud: HTTPS by the platform; HSTS from the app. |
| Production errors | Unhandled errors answer `{"statusCode":500,"message":"Internal server error"}`, with no stack trace or query; the API refuses to start with a weak `JWT_SECRET`. |
| Secrets | All keys are server-side environment variables. The browser bundle has none: the only `NEXT_PUBLIC_` name is an optional API address fallback (`apps/web/src/lib/api.ts:6`). |

## 3. Not applicable, or accepted

- **Password reset tokens: not applicable.** HMIS has no self-service reset (no reset links or
  tokens). An administrator sets a temporary password, which must be replaced at the first sign-in
  and now expires after 72 hours (F3): longer than an e-mailed token's 15-30 minutes because these
  are handed over in person or by phone, often before the next shift.
- **File uploads: not applicable.** There is no file upload. "Documents" are certificates HMIS
  generates; the only uploaded text is a licence (at most 20,000 characters, refused unless signed
  by HMIS). If uploads are added (scans, lab images), they need type and magic-byte checks, a size
  limit and storage outside the web root.
- **CSP allows inline scripts.** Next.js starts pages with inline scripts. The alternative (a
  nonce per request) does not work with this app's prerendered, cached pages. The risk is limited:
  nothing inserts raw HTML, and the policy still blocks scripts and connections to other sites, so
  injected code could neither load more code nor send data away.
- **Signing out of the console** ends that browser's session; the token itself stays valid until it
  expires (8 hours). A password change ends every session.
- **Own-server licences.** Whoever runs the server controls its clock and database; a licence there
  is an agreement more than a lock.

## 4. Git history and secrets to rotate

All 15 commits were scanned (every added line, every file ever added) for private keys, payment
and cloud API keys, tokens, `.env` files, passwords and database addresses with credentials.

- **Nothing to rotate because of the repository.** Only `.env.example` and `deploy/.env.example`
  were ever committed, with placeholders (`JWT_SECRET="change-me"` or empty). The other matches are
  test values (`CHASECK_TEST-secret`, `test-secret`) and the local development database password,
  which only works on a developer's own machine (the development database listens on localhost).
  `.gitignore` excludes `.env*`.
- **Outside the repository:** a licence private key was pasted into a chat on 2026-11-11. It was from
  an unused key pair and was replaced the same day: the key built into HMIS now belongs to a new pair
  whose private key is only in the cloud's environment. Nothing signed with the pasted key is
  accepted.

## 5. Verification

New suite `apps/api/test/security-controls.e2e-spec.ts` (11 tests), all passing:

| Test | What it proves |
|---|---|
| Every route declares who may use it | All 157 routes inventoried; none relies on the default; the 15 public routes are exactly the reviewed list. |
| Refuses every clinic and console route without a sign-in | 142 routes called without a token: every one answers 401. |
| Refuses forged and tampered tokens | Unsigned (`alg: none`), signed with another algorithm, signed with a guessed secret: all 401. |
| Keeps each role to its own work | Cashier and doctor refused on staff, audit, settings, creating admins and exports (403). |
| Cannot read or change another clinic's records | Another clinic's patient and visit: read, change, export and search all fail; the record is unchanged. |
| The database role sees no other clinic's rows | 0 foreign rows in each of the 32 clinic tables; writing a row for another clinic fails. |
| Turns away malformed input | Non-UUID ids and injection strings: 404; repeated or oversized parameters: 400; wrong types: 400 with field errors; broken JSON: 400; over 2 MB: 413; no stack traces or `X-Powered-By`. |
| Uses only the price list | A visit sent with `unitPrice: 1` is charged the list price. |
| Passwords at work factor 12, older ones upgraded | New hash has 12 rounds; a weaker hash becomes 12 after sign-in. |
| A temporary password stops working when it expires | Expired: 401; valid: sign-in, then only the password change is allowed; the expiry is cleared after. |
| The current password cannot be guessed | 5 wrong: then 429 even for the right one, also for turning off two-step sign-in. |

Whole suite: **220 end-to-end tests and 2 unit tests pass**; type checks and lint are clean on both
apps; `pnpm audit` finds no known vulnerabilities. On a production build of the web app, the
headers in section 2 were present, and forged cross-site POSTs to both cookie route handlers were
refused (403) while same-site requests passed.

Not verified here: the live site (https://hmis.app.aletcloud.com answered 503 throughout the
audit), so its HTTPS redirect and headers should be checked once it is back.
